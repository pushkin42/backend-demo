# FAQ

## Почему код не "как в книжке"?

Потому что это реальные рабочие сервисы из коммерческого проекта.

Основная цель кода — решать задачи импорта CommerceML, обработки изображений, синхронизации каталога и поддержки существующей инфраструктуры.

Некоторые решения могут выглядеть неакадемично, но были приняты осознанно исходя из требований производительности, объёма данных и совместимости со старой системой.

---

## Почему используется updateOrCreate() по xml_id?

CommerceML использует XML_ID как внешний уникальный идентификатор сущности.

При повторном импорте необходимо обновлять существующую запись, а не создавать новую.

---

## Почему используется withTrashed()?

CommerceML может присылать данные для ранее удалённых объектов.

Импорт должен иметь возможность восстановить или обновить такие записи.

---

## Почему не используются репозитории?

В проекте используются сервисы и DTO.

Для большинства операций Eloquent уже предоставляет достаточный уровень абстракции.

Дополнительный слой репозиториев в данном проекте не давал практической выгоды и только усложнял сопровождение.

---

## Почему в коде встречаются rescue()?

Во многих местах ошибка не должна прерывать весь процесс импорта.

Например, повреждённая картинка не должна останавливать импорт десятков тысяч товаров.

В таких случаях безопаснее вернуть значение по умолчанию и продолжить обработку.

---

## Почему не используется XMLReader?

Файлы CommerceML в данном проекте обычно имеют размер до нескольких мегабайт.

Для таких объёмов проще и дешевле использовать SimpleXML.

Переход на потоковый парсер имеет смысл только при работе с существенно большими файлами.

---

## Почему используется VIPS, а не Imagick?

Основная задача — массовая обработка изображений каталога.

VIPS показывает существенно меньшее потребление памяти и лучшую производительность при пакетной обработке большого количества изображений.

---

## Почему используется pHash?

Перцептивный хеш позволяет находить одинаковые или визуально похожие изображения даже после изменения размеров, повторного сохранения или незначительной обработки.

Используется для дедупликации изображений каталога и поиска похожих товаров внутри товарных групп.
 
---

## Почему используется собственный идентификатор сессии?

Laravel Session ID может изменяться после регенерации сессии.

Для корзины, избранного и прочих анонимных данных используется отдельный стабильный внутренний идентификатор, который сохраняется между регенерациями Laravel Session.

---

## Почему корзина работает как для пользователя, так и для гостя?

Во многих проектах пользователь сначала добавляет товары в корзину, а авторизуется уже перед оформлением заказа.

Для этого используется единая схема:

* авторизованный пользователь → user_id
* гость → session_id

Код работает с обеими ситуациями одинаково, а при входе/регистрации синхронизирует корзину пользователя с корзиной гостя, если там что-то было.

---

## Почему в коде есть транзакции на уровне отдельных элементов импорта?

Ошибка одной записи не должна откатывать весь пакет.

Если один товар содержит некорректные данные, остальные товары должны продолжить импортироваться.

---

## Почему в коде встречаются очереди?

Импорт CommerceML может содержать тысячи объектов.

Длительные операции вынесены в очередь, чтобы не блокировать веб-запросы и позволять контролировать прогресс обработки.

## Почему используется Redis?

Redis используется для:

* кеширования результатов вычислений;
* хранения промежуточных данных;
* индексов каталога;
* счётчиков;
* ускорения повторных обращений к данным.

## Почему в BaseRemoteCommand вызывается метод executeOnRemote(), которого нет в самом классе?

Это каркас реальной системы. В продакшене логика выполнения команд и протоколы подключения (SSH через phpseclib, WMIC для Windows и т.д.) вынесены в отдельные классы-стратегии и подмешиваются через трейты и интерфейсы (особенно для реализации удаленного подлкючения). Это изолирует инфраструктурную рутину консольной команды Laravel от логики работы с конкретной ОС. В демо-репозитории оставлен только базовый шаблон команды, чтобы показать подход к автоматизации.

## Зачем в e-commerce проекте писать сырой SQL (транзакции, JOIN в UPDATE, рекурсивные CTE), если есть Eloquent ORM?

Eloquent прекрасен для стандартного CRUD, но абсолютно неэффективен на тяжелых операциях и больших объемах данных. Например, атомарное слияние гостевой и авторизованной корзин в цикле на PHP через ORM — это гарантированный race condition и десятки лишних запросов. Я решаю такие задачи там, где они должны решаться — на уровне движка БД за один проход. Использование SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED для тяжелой аналитики — сознательный шаг, чтобы не блокировать таблицы во время фонового импорта товаров.

## Как вы относитесь к конструкциям if (!$var) или empty($var) при проверке входящих данных (например, артикулов)? Линтеры часто требуют строгого === null.

На чистом продакшене при работе с внешними источниками (кривой XML от 1С, сырой JSON от поставщиков или ответы от LLM) пустота может прилететь в виде null, пустой строки "" или пустого массива []. Строгая проверка === null пропустит пустую строку дальше, и код упадет ниже по стеку. Для строковых данных (артикулы, категории) if (!$var) — это самый надежный способ отсечь любой мусор одной строчкой (KISS). Исключение — числовые поля (цены, остатки), где 0 является валидным значением, там проверка идет строго по типу и отдельным методом в валидаторе, заменяя некорректные значения до импорта, если это возможно.

## Почему в парсерах вы используете кастомные DTO (Data Transfer Objects), а не обычные ассоциативные массивы PHP?

Потому что ассоциативный массив — это бесформенная куча данных без контракта. Работать с $data['prod_name'], надеясь, что прошлый разработчик (или поставщик в XML) не опечатался в ключе — путь к багам на проде (кстати, это реальный кейс - вместо артикула может прилететь что угодно, в имени может быть UTF16, и вообще - менеджеры любят 1С).

Мои DTO жестко типизируют входящие свойства, валидируют типы данных «на лету» при наполнении и превращают хаос из прайса в предсказуемый объект. PHPStorm сразу видит автокомплит, а код становится самодокументируемым. Массивы оставляю для простых списков.

## В коде ProductGroupRule цвета собираются в регулярное выражение динамически. Не проще ли было написать один универсальный паттерн?

Нет, не проще. Список цветов в базе интернет-магазина — это динамическая сущность. Напишешь статическую регулярку сегодня — завтра менеджер добавит цвет «розовое золото», и парсер его проигнорирует. Мой подход со сборкой паттерна через Arr::map() и implode() генерирует актуальное регулярное выражение на основе реального справочника цветов прямо в момент выполнения (а справочник вообще можно брать из любого внешнего источника, заменив массив на вызов Action). Это автоматизация, которая не требует правок кода при изменении бизнес-данных.

## Какова ваша позиция по поводу 100% покрытия кода Unit-тестами?

Отрицательная. Гнаться за красивой цифрой 100% в отчетах — это пустая трата оплачиваемого времени бизнеса. Тестировать геттеры, сеттеры или стандартные обертки фреймворка Laravel — бессмысленно. Я пишу тесты на сложные архитектурные узлы, где есть ветвление логики и риск фатальной ошибки: кастомные калькуляторы хэшей файлов (чтобы не перезаписывать медиа на S3), пайплайны разбора сложных строк и критические транзакции в БД. Тесты должны защищать продакшн от падения, а не радовать глаз линтера.
